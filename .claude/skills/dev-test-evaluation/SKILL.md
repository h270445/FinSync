# Dev/test evaluation protocol

- Version: 1.0 (2026-11-12)
- Owner: Bence Varga
- Why it exists: the thesis claims rest on measured numbers. A number is only defensible if every choice (threshold, rule, prompt, few-shot example, abstention level) was made on the development split and the test split was looked at once, after the choice was frozen. The supervisor named this protocol as a skill candidate (2026-10-29 and 2026-11-11, action D1).

## Input

- The question: what is compared or tuned, on which dataset (`tests/data/*.csv`, see [datasets.md](../../../docs/evaluation/datasets.md)), and the metric that decides, from [evaluation-plan.md](../../../docs/evaluation/evaluation-plan.md).
- The candidates (methods, options, a threshold range) and the baseline they are compared with.

## Output

1. A runner or runner change under `finsync/evaluation/` that produces the whole report, with tests.
2. One new report file `docs/evaluation/results/YYYY-MM-DD-<topic>.md`, written by the runner, plus a row in the results table of `docs/evaluation/README.md`.
3. A short report in the reply: the decision rule, what was chosen on dev, the test numbers next to the baseline, the gate results.

## Prohibitions

- **Never look at the test split before the choice is frozen.** No test metrics in exploratory runs, no "quick check" on test, no printing test rows while tuning. The runner computes test results only after the choice is made from dev results alone, in the same run.
- **Never change a choice after seeing test results.** If the test result is bad, it is reported as it is. A new idea is tuned on dev again and reported in a new result file that says it follows an earlier test look (and which one).
- Never choose few-shot examples, prompt wording, keyword lists or merchant dictionaries from test items. They come from dev items or from outside the dataset.
- Never edit a committed dataset or move items between splits. A change is a new dataset version (new file or `--version`), generated by the generator with a fixed seed and described in `datasets.md`; the drift test must keep passing.
- Never edit a result file after it is committed (results are never edited after the fact). A re-run gets a new file.
- Never report a method without its baseline in the same table (store-every-row for matching; the rule-based categorizer and the usual-category baseline for categorization).
- Never hide a kind of error inside an average: false merges are reported separately from missed duplicates, abstentions separately from wrong answers, wrong answers given with high confidence separately.
- Never send real personal or financial data to an LLM or put it in a dataset. Only the synthetic datasets are used; an LLM sees only the fields the design allows (description, merchant, amount, context).
- Never make the matching engine more complex to improve a number (frozen by the supervisor, 2026-11-11).

## Steps

1. **Write the decision rule first.** Before any run, write down in the runner (as code) and in the report header: the metric order that decides (for example "fewest false merges, then highest recall, then lowest review rate; ties go to the higher threshold"), the candidate grid, and what is fixed. If the plan does not define the rule, propose one and stop (checkpoint 1).
2. **Tune on dev only.** The runner filters `row.split == "dev"` for every sweep and comparison, and the choice function receives dev results only (see `choose_threshold` in `finsync/evaluation/runner.py`).
3. **Freeze, then report test once.** In the same run, the chosen setting is applied to `row.split == "test"`, next to the baseline, in every order or condition the plan names (matching: arrival and reverse order).
4. **Make it reproducible.** The report header carries: commit (`git describe --always --dirty`; a `-dirty` report is not committed), the exact command, the dataset path with its sha256 prefix and dev/test sizes, every fixed parameter, and for an LLM the model, prompt version, temperature and the date. LLM runs also report latency (median and worst) and cost per item; cached answers are stored so a re-run gives the same numbers.
5. **List the errors.** Every false merge, missed duplicate or confident wrong category is listed by item id with the scenario, so the thesis can discuss them.
6. **Test the runner.** A unit test checks the choice function and that the test split does not influence the choice (for example: changing test labels does not change the chosen setting). A determinism test on a sample of cases keeps the suite fast (see `tests/test_evaluation_runner.py`).
7. **Document.** Add the report row to `docs/evaluation/README.md` in one sentence (what was chosen on dev, the test result against the baseline), and update `evaluation-plan.md` if the method changed.

## Self-check

```bash
python -m unittest discover -s tests                 # all OK, including the dataset drift tests
git status --short tests/data                        # empty: no dataset edited by hand
grep -n "split" finsync/evaluation/<runner>.py       # every tuning path filters dev; test appears only after the choice
python -m <runner> --out a.md && python -m <runner> --out b.md && diff a.md b.md   # identical (non-LLM runs); write a.md and b.md outside the repository
```

Then read the report once as the supervisor would: is the baseline in every table, is the decision rule stated before the numbers, does it say that test was not used for the choice, and are the errors listed by id?

## Human checkpoints

1. **Before** the first run: the author approves the decision rule and the candidate grid when the evaluation plan does not already fix them.
2. **Before** any LLM call that costs money: the author approves the model, the number of items and the expected cost.
3. **After** the test result: the author reads the report before it is quoted in a status e-mail or the thesis. If the result invites another try, the author decides whether to start a new dev round (and the next report says so).
