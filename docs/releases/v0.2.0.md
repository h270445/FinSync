## What works

The demonstrated flow ([M1](../planning/milestones/m1-2026-11-06-working-core.md#the-flow-demonstrated)): a bank notification and a manual entry for the same purchase arrive through the API; FinSync stores both records, links them to one event, and `GET /v1/events` shows one purchase. Two look-alike purchases from the same phone stay separate.

- **Matching on every input path.** Notification (`POST /v1/notifications/ingest`), manual (`POST /v1/transactions`) and bulk (`POST /v1/transactions/bulk`) input go through ingest → normalise → match → store in one database transaction. A bulk import with one invalid row stores nothing.
- **Traceable decisions.** Every record has an `event_id`; every outcome (`exact_duplicate`, `auto_linked`, `needs_review`, `separate`) has a `match_decisions` row with score, features and matcher version (`rules-3`). Source records are never changed by matching.
- **Review and correction** (planned for M2, done early): `GET /v1/matches/review`, `POST /v1/matches/{id}/confirm`, `.../reject`, `POST /v1/events/{id}/split`. Automation never overrides a person's decision.
- **Order dependence handled.** A strict gate for information-poor pairs and reopening of contested automatic links (`rules-3`, [design](../design/transaction-matching.md#5-decide)), chosen on the development split after the supervisor's request of 2026-10-29.
- **Measurement.** A labelled synthetic dataset (v1: 100 records; v2: v1 plus 32 look-alike records), a generator, and an evaluation runner that sweeps the threshold on dev and reports test against the store-every-row baseline.
- **Android spike.** A Kotlin listener on a real Samsung phone (Android 14) reading only OTP Bank, Revolut and K&H notifications. Captures stay on the phone; a notification without an amount and currency is stored only masked, while one with an amount (even marketing such as "earn €10") is kept in full. The M2 app forwards only known bank patterns ([findings](../design/android-notification-spike.md)).
- **Decisions recorded:** ADR 0007 (HTTPS tunnel for external clients), ADR 0008 (notification time and calendar day).

## How to verify

```sh
python -m unittest discover -s tests          # 70 tests, all pass
python -m finsync.evaluation                  # same numbers as docs/evaluation/results/2026-10-29-matching-rules-3.md
python -m finsync.evaluation.generate         # regenerates tests/data/matching_eval_v2.csv unchanged
python -m finsync.api                         # API on http://127.0.0.1:8080
```

The hand-decided examples (repeated submission, reverse arrival order, date-only manual entry, two separate same-amount purchases) are named tests in `tests/test_matching_service.py`.

## Known limitations

- Storage is still SQLite on the standard library; the FastAPI/PostgreSQL switch follows after M1 ([roadmap](../planning/roadmap.md)).
- No authentication yet: group membership is not tied to a signed-in person (M2, Nov 2–8). The API must not be exposed through the tunnel before that ([ADR 0007](../architecture/decisions/0007-how-external-clients-reach-the-api.md)).
- `rules-3` trades recall for safety: more true duplicates wait for review instead of being linked.
- Two same-amount purchases in one shop on the same day, without a time on the manual entries, can still be merged; rules cannot separate them.
- A contested review cannot be confirmed while the event holds a record from the same channel; the member splits first.
- The notification parser supports the prototype format only; the OTP Bank format from the spike, the `posted_at` field and reading times without an offset as Europe/Budapest follow in M2 ([ADR 0008](../architecture/decisions/0008-notification-time-and-calendar-day.md#consequences)).
- The datasets are synthetic; v2 over-represents look-alike cases on purpose.
