## What works

The integrated flow ([M2](../planning/milestones/m2-2026-12-04-integrated-prototype.md#expected-result-course)): a card purchase arrives as a notification from the Android app and again as a row of a bank spreadsheet export; FinSync links both to one event, keeps two separate same-amount purchases of the same day apart, suggests a category with its source and uncertainty, and the web app shows the group's totals over deduplicated events. The [demo guide](../guides/demo.md) walks through it on a seeded synthetic group; it was run in the browser and with the Android emulator on 2026-11-24.

- **One matching pipeline for every source.** OTP Bank notifications from the Android app (`POST /v1/notifications/ingest`, `tests/test_android_ingest.py`), manual and bulk entries (`tests/test_matching_service.py`), and CSV or XLSX spreadsheet exports with a preview (`POST /v1/imports`, `tests/test_file_import.py`, including a file row linked to the notification of the same purchase). The matching engine is frozen at `rules-3` (supervisor, 2026-11-11).
- **Review in the web app.** Uncertain matches are listed, confirmed or rejected on the review screen; a wrong link is split on the event detail (W4), which shows the decision history; every answer is an append-only `match_decisions` row that supersedes the previous one ([design](../design/transaction-matching.md#5-decide), `tests/test_review.py`, `web/src/pages/ReviewPage.test.tsx`).
- **Hybrid categorizer with abstention.** The group's merchant rules, then a Hungarian merchant and keyword dictionary, then an optional LLM layer with five samples and an abstention threshold; an unsettled suggestion is shown as "Bizonytalan" until a member decides ([design](../design/categorization.md), [ADR 0011](../architecture/decisions/0011-llm-categorization-layer.md), `tests/test_hybrid_categorizer.py`; measurement below).
- **LLM in the live flow, off by default.** A group admin sets the schedule and a monthly budget on W8 (web session only); a member can ask about one event; only the record's merchant, description and amount leave the server; a member's decision always wins; every call is logged with its cost ([ADR 0013](../architecture/decisions/0013-llm-in-the-live-flow.md), `tests/test_llm_live.py`; tests never call a paid model).
- **Category correction.** Confirm or change a category in one tap on the event list (W3) and the detail (W4), mark a purchase as mixed, split it into category lines that add up to the amount, mark a record as a transfer; every change is logged, and merchant memory learns a rule only for non-mixed merchants (`PUT /v1/events/{event_id}/category`, `.../mixed`, `.../category-lines`, `.../transfer`; `tests/test_category_correction.py`, `web/src/pages/EventDetailPage.test.tsx`, `web/src/pages/EventsPage.test.tsx`).
- **The web app as a whole.** Sign-in (W1), overview with monthly totals by category and member over deduplicated events, transfers excluded and items waiting for review flagged (W2, `GET /v1/overview`, `tests/test_overview.py`), event list and detail (W3, W4), review queue, manual entry (W6), file import with preview (W7), settings with members and roles, API tokens, merchant rules, own accounts and the LLM schedule (W8). Hungarian UI text; checked at 360 and 1280 px ([web/](../../web/README.md)).
- **Money transfers.** Records to or from the group's own accounts and counterparties are transfers, left out of spending and income totals (`tests/test_transfers.py`).
- **Authentication and access control.** Per-member API tokens for the Android app ([ADR 0009](../architecture/decisions/0009-api-tokens.md)); password sign-in with an HttpOnly session cookie and CSRF protection ([ADR 0010](../architecture/decisions/0010-web-sign-in.md)); admin and member roles; issuing tokens and changing roles only from a web session ([ADR 0012](../architecture/decisions/0012-no-multi-factor-authentication.md)); every endpoint has a cross-group access test (`tests/test_auth.py`).
- **Safe failure.** Malformed input gets 400, an oversized body 413, and a failing bulk or file import stores nothing (`tests/test_api_limits.py`, `tests/test_file_import.py`).
- **Time handling (ADR 0008).** The phone's posting time and the arrival time are stored separately; times without an offset are read as Europe/Budapest (`tests/test_local_time.py`).
- **Storage on SQLite or PostgreSQL 16.** SQLAlchemy Core and Alembic behind `FinSyncStorage`, Docker Compose for PostgreSQL and the API ([ADR 0006](../architecture/decisions/0006-framework-based-stack.md), `tests/run_on_postgres.py`).
- **Android app.** Forwards only known OTP Bank transaction notifications, with an outbox and retries that never create a second event; tested on the emulator and with a real card purchase on the phone on 2026-11-20–21 ([results](../design/android-notification-spike.md#2026-11-2021-m2-forwarding-on-the-real-phone), [clients/android/](../../clients/android/README.md)).
- **Design and method.** Six design views checked against the code ([design-views.md](../architecture/design-views.md)); ADRs 0001–0013 ([index](../architecture/decisions/README.md)); ten versioned agent skills in [`.claude/skills/`](../../.claude/skills/README.md), two chosen for the methods chapter (endpoint-and-screen-checklist, dev-test-evaluation).

## Known limitations

- **Design views and the skill criterion are waiting for review.** The six views were checked against the code on 2026-11-24 and go to the supervisor with this package; the M2 criterion stays open until the review.
- **Categorization limits.** Mixed merchants remain the hard case (test split: 52.4% coverage, 54.5% accuracy of settled); cryptic bank texts are never settled (0 of 10). The dictionary names the same large Hungarian chains as the synthetic dataset, so its numbers on known merchants are optimistic (section 4 of the report). The data are synthetic.
- **LLM privacy.** The bank's description text is sent as it is and may contain a sole trader's name; masking before the call is a possible later step ([ADR 0013](../architecture/decisions/0013-llm-in-the-live-flow.md)). The comparison with a local model is planned for December if time allows (supervisor, 2026-11-23).
- **Android.** The API token is kept in plain app preferences; the setup and status screens (A1/A2) are not yet split (supervisor: after M2 if needed); only the OTP Bank format is supported.
- **Google Sheets script** not built (optional since M0); it is the first item cut from the Nov 26 – Dec 2 buffer.
- **Sign-in.** No limit on failed sign-in attempts and no multi-factor authentication ([ADR 0012](../architecture/decisions/0012-no-multi-factor-authentication.md)); step-up re-authentication is the proposed next step.
- **Matching** keeps the limits of `rules-3` named in [v0.2.0](v0.2.0.md#known-limitations): recall traded for safety, and two same-amount purchases in one shop on the same day without times can still be merged.
- **ADR status.** ADRs 0005 (web client first) and 0009 (API tokens) are implemented but still marked Proposed.
- **Web build.** The production bundle is one chunk over 500 kB (Vite warning); four lint warnings about fast refresh in shared UI files.
