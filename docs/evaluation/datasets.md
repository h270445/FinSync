# Datasets

## `tests/data/matching_eval.csv` — matching, version 1

- Generated by `python -m finsync.evaluation.generate --records 100 --seed 2026` ([generate.py](../../finsync/evaluation/generate.py)); a test fails if the committed file and the generator drift apart.
- 100 records describing 71 purchases of one two-member household, 1–28 September 2026. Fully synthetic: invented amounts and times, merchant names of public chains only.
- Records are in arrival order (`arrives_at`), the order the runner replays them in.

### Columns

| Column | Meaning |
| --- | --- |
| `record_id` | `R0001`… in arrival order |
| `case` | One run of a scenario; a look-alike pair (two bus tickets, a purchase and its refund) shares a case while keeping two `true_event` labels |
| `true_event` | Label: records with the same value describe the same purchase. Never shown to the matcher |
| `scenario`, `kind` | How the record was produced; `kind` is the duplicate kind from the [matching design](../design/transaction-matching.md#where-duplicates-come-from): `A` re-delivery, `B` cross-source duplicate, `C` look-alike, `none` single record |
| `split` | `dev` (for tuning) or `test` (for reporting), fixed per `case` from a hash, so neither a purchase nor a look-alike pair is split across them |
| `member`, `source`, `arrives_at` | Who sent it, through which channel, and when it reached the server |
| `message` | Notification text, for `android_notification` rows |
| `amount` … `source_ref` | Manual row fields, the same as `POST /v1/transactions` |

### Scenarios

| Scenario | Kind | What it tests | Expected |
| --- | --- | --- | --- |
| `single_notification`, `single_manual` | none | Purchases with one record: targets for false merges | Own event |
| `notification_and_manual` | B | The common duplicate: same minute ±20, merchant typed | One event |
| `manual_first` | B | Reversed arrival order | One event |
| `date_only_manual` | B | Date-only entry; half with merchant, half description only | One event, often via review |
| `rounded_manual` | B | 1234.56 typed as 1235 | One event, often via review |
| `late_manual` | B | Logged one or two days later with the day of logging | One event, often via review |
| `two_members_same_purchase` | B | Both members log one dinner | One event |
| `repeated_notification` | A | The same notification sent again | One event (`exact_duplicate`) |
| `resent_sheet_row` | A | The same sheet row sent again with its `source_ref` | One event (`exact_duplicate`) |
| `same_amount_same_phone` | C | Two equal purchases at one shop minutes apart | Two events |
| `same_amount_other_shop` | C / B | Two equal purchases in different shops; the manual entry belongs to the second | Three records, two events |
| `identical_manual_rows` | C | Two equal bus tickets, identical rows | Two events (review allowed) |
| `monthly_subscription` | C | Same charge 30 days apart | Two events |
| `refund` | C | Purchase and same-amount refund | Two events |
| `very_late_manual` | B | Logged five days later, outside the window | One event; counted as a missed duplicate, a known limit |

Labels follow from the scenario, so they are correct by construction; the hand-decided examples in `tests/test_matching_service.py` check the rules on top of that.

### Known limits of version 1

- Notification texts use the prototype parser's format, not a real bank's (the Android spike will provide those).
- Few merchants and amounts, so accidental collisions between unrelated purchases are more frequent than in a real household; this makes the false-merge test harder, not easier.
- The reverse-order false merge (2026-10-18) occurred only in the test split, so fixes for it could not be chosen on the development split; version 2 below adds such cases.
- Version 3 (200–300 records, Nov 16–22 in the roadmap) adds file-import rows and real notification formats.

## `tests/data/matching_eval_v2.csv` — matching, version 2

- Generated by `python -m finsync.evaluation.generate --version 2`; the same test checks it against the generator.
- The 100 records of version 1, unchanged and in the same order (R0001–R0100), followed by 8 cases of `same_amount_neighbour_days` drawn from seed 2027 (R0101–R0132): 132 records, 87 purchases. 7 of the 8 cases fall in the development split and 1 in the test split.
- Added on 2026-10-29 for the supervisor's request to compare two fixes for the reverse-order case on the development split ([feedback](../planning/supervisor-feedback.md#2026-10-29--reply-to-the-oct-28-interim-note)).

| Scenario | Kind | What it tests | Expected |
| --- | --- | --- | --- |
| `same_amount_neighbour_days` | B / C | Two same-amount purchases in one shop two days apart, each with a date-only manual entry; member A logs the first a day late, on the day between them | Two events of two records each, in either arrival order |

The added cases are deliberately frequent (8 of 87 purchases), so review and double-count rates on version 2 are higher than a household would see; compare options on it, not against version 1 results.

## `tests/data/matching_eval_v3.csv` — matching, version 3

- Generated by `python -m finsync.evaluation.generate` (`--version 3`, the default); the same test checks it against the generator. `python -m finsync.evaluation` uses it by default.
- Version 2 record for record, except that the 65 notification texts print Europe/Budapest wall-clock time instead of UTC (September is summer time, so two hours later). Since 2026-11-12 the parser reads a time without an offset as Budapest time ([ADR 0008](../architecture/decisions/0008-notification-time-and-calendar-day.md)), so version 3 gives the matcher exactly the instants version 2 gave before; a test checks this for every record.
- Versions 1 and 2 stay unchanged for the earlier results, but under the new parser their texts are read two hours early. Re-running them no longer reproduces the 2026-10-18 and 2026-10-29 numbers (on version 2: one dev-split row of the threshold sweep differs, the test split is unchanged).
- Check on 2026-11-12: the evaluation on version 3 reproduces every generated number of the [2026-10-29 result](results/2026-10-29-matching-rules-3.md) ([result](results/2026-11-12-matching-rules-3-v3.md)).

## `tests/data/categorization_eval.csv` — categorization, version 1

- Generated by `python -m finsync.evaluation.generate_categories --seed 2026` ([generate_categories.py](../../finsync/evaluation/generate_categories.py)); a test fails if the committed file and the generator drift apart.
- 200 purchases, each as a categorizer would see it: description, merchant and amount. Fully synthetic: merchant names of public chains and invented small shops, invented amounts, no member or group data.
- Labels use the proposed category list of the [categorization design](../design/categorization.md#open-questions): `groceries`, `eating_out`, `transport`, `housing_utilities`, `health`, `clothing`, `entertainment`, `household`, `other`. The current rule-based categorizer still answers with its own four categories plus `other`, so the evaluation runner will need a mapping or the extended rule set.
- Split 101 dev / 99 test by a hash of `item_id`; both splits hold clear and ambiguous items. The ask thresholds and the few-shot examples are chosen on dev only.

### Columns

| Column | Meaning |
| --- | --- |
| `item_id` | `C0001`… |
| `scenario` | How the item was produced (table below) |
| `ambiguity` | `clear`: the item itself tells the category; `ambiguous`: it cannot be told from the item, only guessed |
| `split` | `dev` or `test` |
| `source` | `android_notification` (bank text only), `file_import` (bank export description), `manual` (what a member types) |
| `description`, `merchant`, `amount`, `currency` | The categorizer's input; nothing else is sent to it |
| `true_category` | Label: what the member actually bought. Never shown to the categorizer |
| `usual_category` | The merchant's usual category, for scoring a merchant-only guess on ambiguous items; empty when the merchant is hidden |

### Scenarios

| Scenario | Ambiguity | Items | What it tests |
| --- | --- | --- | --- |
| `clear_merchant` | clear | 50 | One category fits almost always (BKK, MOL, Netflix, MVM, Benu, H&M…) |
| `mixed_merchant` | ambiguous | 50 | Mixed-assortment chains (Tesco, Spar, Auchan, Lidl, Rossmann, dm, eMAG, Amazon, Decathlon) without detail; the true category is drawn from a per-merchant share, for example Tesco 70 % groceries, 15 % household, 10 % clothing, 5 % entertainment |
| `mixed_with_detail` | clear | 30 | The same chains entered manually with a description that settles it, in English or Hungarian ("Tesco - zokni") |
| `unfamiliar_merchant` | clear | 30 | Small shops the keyword rules do not know but a reader can place from the name ("KOVACS PEKSEG BT", "DR NAGY FOGASZATI REND") |
| `hungarian_description` | clear | 20 | Manual entries with a Hungarian description only ("benzin", "villanyszámla", "fogorvos") |
| `cryptic_text` | ambiguous | 20 | Payment-provider texts that hide the merchant ("SUMUP *KJ BT", "PAYPAL *…", "SIMPLEP*…"); the true category is drawn from a plausible set |

For clear scenarios the category is drawn first and the merchant second, so rare categories such as `housing_utilities` and `other` still appear (13 and 10 items). Labels follow from the scenario, so they are correct by construction.

### Known limits of version 1

- The merchant shares of mixed-assortment chains are the author's assumptions, not measured household data; the ambiguous items test the abstaining behaviour, not a real purchase distribution.
- Bank texts follow the formats used in the matching dataset and the masked spike notifications, not a full sample of every bank.
- One purchase is one category; mixed baskets with category lines are not in version 1.
